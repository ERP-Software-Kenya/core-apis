Unit tests cover pure logic only. If writing the test requires mocking an external client (HTTP, DB, LLM, vector store, object store, message queue, FS), the unit-of-behavior is integration glue and the test belongs in an integration tier with a real or testcontainer backend, not under a unit-test marker.
Discriminating question: "what does this test fail on if I break it?" If the answer is "real branching logic computed the wrong output from supplied inputs" → unit test. If the answer is "the mock wasn't called with expected args" or "the mock-supplied response wasn't passed through" → integration test in unit clothing; reject.
Narrow exception: mock as fixture-delivery for pure internal logic (e.g., feeding synthetic scores into a reranker to assert score-to-rank ordering, feeding canned args to assert query-string construction). The assertion must be on computable behavior of the function, not on the mock interaction.
Recorded fixtures from real backend calls are integration tests with replay, not unit tests.
When a gap report classifies coverage, mockable-but-integration code goes in an out-of-scope/integration-tier section, not the unit-test scope. Don't write mock-heavy unit tests to satisfy a marker — the maintenance cost is real and the signal is weak.
